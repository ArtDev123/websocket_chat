# Разрез монолита — обзор

Пошаговая реализация — в [README.md](README.md). Здесь карта: какой файл куда уезжает, из чего состоит RabbitMQ и почему логин не кладётся в очередь.

> Код пишете по шагам. Этот файл только объясняет границу. Exchange, очередь и проекцию создадите в своих шагах.

Монолит к этому моменту уже собран по [docs/](../README.md). Его каталоги `app/`, `alembic/`, корневые `Dockerfile` и `docker-compose.yml` не трогаем. Рядом появляются три новых каталога.

```text
rabbit/docker-compose.yml          брокер, ничей
user_service/                      было: users, пароли, JWT
chat_service/                      было: rooms, messages, ws, static
```

---

## 1. Зачем резать уже работающий чат

В монолите регистрация, комнаты и сокет — один процесс и одна база. Это удобно, пока всё меняется вместе. Дальше у кусков разный ритм: пароли и список людей меняются редко, сообщения и сокеты — постоянно. Общая база заставляет чат знать таблицу `users`, включая `password_hash`.

Разрез оставляет каждому сервису свою работу:

| Сервис | Владеет | Не хранит |
|--------|---------|-----------|
| user | `users`, пароль, выпуск JWT, `GET /users` | комнаты, тексты, сокеты |
| chat | комнаты, сообщения, WebSocket, история | пароли и хэш пароля |

Связь между ними две, и они разные. Кто этот человек прямо сейчас — отвечает подпись токена, синхронно. Что в чате записано имя этого человека — приезжает событием, когда регистрация уже случилась.

## 2. Что куда переезжает

| Из монолита | Куда | Что меняется |
|-------------|------|----------------|
| `User`, `routes/auth.py`, `routes/users.py`, `repositories/users.py` | `user_service` | после commit регистрации — событие |
| `Room`, `Message`, `routes/ws.py`, `manager.py`, `static/` | `chat_service` | нет FK на `users`, пользователь берётся из JWT |
| `db.py`, `errors.py`, `repositories/base.py`, `alembic.ini`, `alembic/env.py`, `docker-entrypoint.sh` | оба сервиса | копия, общего пакета нет |

Каркас копируется, а не импортируется из корня. Общий пакет снова собрал бы оба сервиса в одну поставку: чат нельзя было бы поднять, не таща код паролей.

Общая ревизия `alembic/versions/788c83caced5_initial_revision.py` создаёт `users`, `rooms` и `messages` в одной базе. Две базы одну ревизию не поделят. У каждого сервиса своя начальная миграция: user создаёт только `users`, chat создаёт `rooms`, `messages` и `user_profiles`.

`created_by_id`, `sender_id` и `recipient_id` остаются целыми числами. Это те же id, что выдал user-сервис. Внешнего ключа на `users` в базе чата нет: такой таблицы там нет, и база чата не может спросить чужой Postgres «есть ли строка 5». `room_id` по-прежнему ссылается на `rooms` — обе таблицы живут в чате.

## 3. Почему логин не едет через брокер

Браузер на каждый запрос и на каждый кадр сокета должен сразу знать, пускать или нет. Очередь отвечает не сейчас, а когда консьюмер освободится. Для «войти» и «написать в комнату» это опоздание лишнее.

Поэтому оба процесса знают один секрет HS256. В токене, как и в монолите, `sub` и `username`. User-сервис токен **подписывает**. Чат только **проверяет подпись** и собирает `{id, username}` из payload. В базу паролей он не ходит: иначе каждое сообщение сокета стало бы HTTP-запросом в user-сервис, и чат снова зависел бы от того, жив ли сосед.

Имя в уже сохранённом сообщении из токена не берём. Токен есть только у того, кто сейчас подключён. История и чужие кадры читают `username` из локальной копии, которую чат записал себе заранее.

```text
user_profiles   id (тот же, что выдал user-сервис, не serial), username, created_at
```

Свой sequence у профиля был бы ошибкой: чат выдал бы id 1 человеку, который в user-сервисе имеет id 7. Пишет строку только консьюмер, явным `id` из события.

## 4. Компоненты RabbitMQ

RabbitMQ — отдельный процесс. Он хранит сообщения, пока их кто-нибудь не заберёт. User и chat к нему подключаются по протоколу AMQP, порт `5672`. Сами они друг другу сокет не открывают.

Внутри брокера на этом уроке пять вещей. Путают обычно exchange и очередь: публикуют не «в очередь чата», а в exchange, а очередь — это ящик конкретного получателя.

```text
user-сервис                         брокер                              chat-сервис
     │                                │                                      │
     │  publish                        │                                      │
     │  routing key user.registered    │                                      │
     │ ──────────────────────────────►│  exchange users  (topic, durable)    │
     │                                │         │                            │
     │                                │         │ binding                    │
     │                                │         │ key = user.registered      │
     │                                │         ▼                            │
     │                                │  queue chat.users  (durable)         │
     │                                │         │                            │
     │                                │         │ deliver                    │
     │                                │         ▼                            │
     │                                │                               консьюмер
     │                                │                               ack после upsert
```

| Компонент | Что это на уроке | Кто создаёт |
|-----------|------------------|-------------|
| Брокер | процесс RabbitMQ, образ `rabbitmq:3-management` | compose в `rabbit/` |
| Соединение | `connect_robust`, само поднимается заново, если брокер моргнул | каждый сервис в своём lifespan |
| Exchange `users` | доска объявлений: «здесь новости о людях» | оба сервиса, вызов идемпотентный |
| Routing key | ярлык одного факта: `user.registered` | кладёт publisher |
| Binding | правило «такие ярлыки складывать в этот ящик» | chat, вместе с очередью |
| Очередь `chat.users` | ящик чата. Другой сервис завёл бы свою очередь на тот же exchange | только chat |
| Сообщение | JSON с `event`, `user_id`, `username` | user, после commit |

**Exchange** нужен, чтобы отправитель не знал имена очередей. User-сервис знает факт и ярлык. Сколько сервисов его слушает и как называются их ящики — не его дело. Завтра появится третий сервис со своей очередью и своей привязкой, регистрацию менять не придётся.

Тип exchange — **topic**. Он сравнивает routing key с шаблоном привязки. Сейчас привязка точная: `user.registered`. Тот же exchange потом примет `user.updated` отдельным ключом, а чат сможет подписаться на `user.*`, не прося user-сервис слать копии. Direct тоже сверил бы одну строку с одной строкой, но следующий ключ про людей уже не лез бы в ту же схему «один шаблон на все новости о пользователе».

**Durable** у exchange и очереди значит: брокер запомнил, что они существуют, и после своего перезапуска создаст их снова. Это не то же самое, что «сообщение не потеряется». Сообщение ещё нужно положить с `delivery_mode=persistent` и положить его в очередь, которая уже есть.

**Очередь объявляет получатель.** Если её объявит отправитель, он снова узнает имя ящика чата. Пока чат не стартовал, у exchange нет привязки. Publish в такой exchange брокер принимает и выбрасывает: хранить некуда. Поэтому порядок на уроке такой: брокер, потом chat, потом user, потом регистрация.

**Ack** — подтверждение «я это сообщение обработал». До ack брокер считает его не доставленным до конца. Консьюмер пишет `user_profiles` и только потом подтверждает. Исключение в обработчике возвращает сообщение в очередь (`requeue`). Повтор той же доставки безопасен: `INSERT ... ON CONFLICT (id) DO UPDATE` обновляет username и не создаёт вторую строку.

Управление смотрит в браузер на порту `15672` (логин `guest` / `guest`). Там видны exchange `users`, очередь `chat.users` и привязка. Это тот же брокер, не отдельный сервис.

Клиент в коде — **aio-pika**. Обычный `pika` блокирует поток на время сети. Uvicorn крутит сокеты и HTTP в одном event loop, поэтому публикация и чтение очереди тоже асинхронные. `connect_robust` заново открывает канал, если контейнер брокера на секунду пропал.

Пользователь `guest` в RabbitMQ по умолчанию принимает соединения только с localhost. Контейнер API для брокера — другая машина в сети Docker. В `rabbitmq.conf` стоит `loopback_users = none`, иначе логин из user- и chat-контейнеров не проходит, хотя с хоста UI открывается.

## 5. Почему событие одно и только после commit

```text
браузер                         user                         rabbit                         chat
   │  POST /auth/register          │                              │                              │
   │ ─────────────────────────────►│ insert users                 │                              │
   │                               │ publish user.registered      │                              │
   │ ◄──────── 201 UserRead ───────│ ────────────────────────────►│ deliver                      │
   │                               │                              │ ────────────────────────────►│ upsert user_profiles
   │  POST /auth/login             │                              │                              │
   │ ◄──────── JWT ────────────────│                              │                              │
   │  WS /ws?token=…               │                              │                              │
   │ ──────────────────────────────────────────────────────────────────────────────────────────►│ проверить подпись
   │ ◄──────────────────────────────────────────────────────────────────────────── sender: alice │ имя из проекции
```

Тело сообщения:

```json
{"event": "user.registered", "user_id": 1, "username": "alice"}
```

Пароля и хэша в нём нет. Чату достаточно id и имени, чтобы подписать кадр и проверить, что получатель DM уже существует. Пока события нет, `GET /dm/{id}` отвечает 404: проекция пустая, даже если токен у отправителя настоящий.

Publish стоит **после** commit в `users`. До commit чат записал бы профиль человека, которого в user-базе нет. Если commit прошёл, а брокер лежит, регистрация отвечает 503: клиент не должен считать, что новость уехала. Строка пользователя при этом уже есть, повтор того же ника даст 409. Связка «строка и событие либо вместе, либо никак» называется outbox: событие пишут в ту же транзакцию и отдельный процесс дочитывает его в брокер. На уроке outbox нет, в финале он только назван.

Шина односторонняя. Факт «в чате написали сообщение» user-сервису не нужен: он не рисует ленту и не хранит тексты. Обратное событие было бы вторым контрактом без читателя.

Проекция догоняет user-сервис с опозданием на время очереди. На своей машине это миллисекунды, но порядок такой: сначала строка в `user_profiles`, потом кадр с `sender`. Имя в истории читается из этой строки, поэтому связь `Message.sender` в SQLAlchemy смотрит на `UserProfile` через `primaryjoin`, без `ForeignKey` в базе.

## 6. Почему брокер — третий compose

У user и у chat свой `docker-compose.yml`: свой API и свой Postgres. Брокер внутрь одного из них класть нельзя. Второй сервис его не увидит, а два брокера друг с другом не разговаривают.

`rabbit/docker-compose.yml` создаёт сеть с именем `lesson-net`. Оба API подключаются к ней как к внешней. Своя база остаётся в частной сети сервиса: чату не нужен порт Postgres пользователей, ему нужен только AMQP.

С хоста базы проброшены на разные порты, чтобы не занять `5432` монолита. Внутри compose хост базы — имя сервиса `db`, порт `5432`.

| Сервис | API | Postgres с хоста | Зачем отдельный порт |
|--------|-----|------------------|----------------------|
| user | 8081 | 5433 | монолит, если запущен, сидит на 8080 и 5432 |
| chat | 8082 | 5434 | страница и сокет живут здесь |
| rabbit | 5672, UI 15672 | — | AMQP для контейнеров, UI для проверки |

Сервисы в compose названы `user-api` и `chat-api`. Оба входят в `lesson-net`. Два контейнера с именем `api` в одной сети делили бы одно DNS-имя, и publish уехал бы не туда.

Страницу по-прежнему отдаёт чат. Браузер считает `127.0.0.1:8082` и `:8081` разными сайтами, поэтому user-сервис явно разрешает origin чата. Иначе `curl` с хоста проходит, а кнопка Login в HTML нет: браузер сначала шлёт `OPTIONS`. Сокет остаётся на `location.host`, его на user-сервис не переносят.
