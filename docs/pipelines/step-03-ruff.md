# Шаг 3 — Ruff

**Предыдущий:** [step-02-tests.md](step-02-tests.md) · **Следующий:** [step-04-github.md](step-04-github.md)

## Задача

Включить ruff в каждом сервисе. Он должен проходить локально до того, как тот же вызов поедет в workflow.

## Теория

Зачем линтер не стоит в боевом `requirements.txt` — в [guide.md](guide.md), раздел «Почему ruff не в requirements.txt».

Ruff читает `ruff.toml` из каталога, где его запустили. У user и chat конфиг одинаковый и свой: общий файл в корне зацепил бы монолит, а у монолита этот урок ничего не меняет.

`select` короткий. `F` ловит имя, которого нет (опечатка в импорте, забытый символ). `I` требует, чтобы импорты были сгруппированы. `E4`, `E7`, `E9` — часть pycodestyle про явные ошибки вроде повторного определения. Длину строки конфиг не включает: переносы в учебном коде не должны красить пайплайн.

`extend-exclude = ["alembic"]` выключает ревизии. Их пишет Alembic, и правка порядка импортов в сгенерированном файле к уроку не относится.

## Код

`user_service/ruff.toml` и `chat_service/ruff.toml`:

```toml
target-version = "py312"
line-length = 100
extend-exclude = ["alembic"]

[lint]
select = ["E4", "E7", "E9", "F", "I"]
```

Ruff уже есть в `requirements-dev.txt` с прошлого шага. Отдельной зависимости нет.

## Разбор кода

`target-version = "py312"` совпадает с образом `python:3.12-slim`. Ruff тогда не предлагает синтаксис, которого в этом интерпретаторе нет.

`line-length` без правила `E501` в `select` никого не ругает. Поле оставлено, чтобы следующее правило, если его добавите, мерило ту же ширину.

Запуск `ruff check .` из каталога сервиса видит `app/` и `tests/`. Точка — текущий каталог, не весь репозиторий.

## ✅ Проверка

```bash
cd user_service
ruff check .

cd ../chat_service
ruff check .
```

Ожидание: `All checks passed!` в обоих. Если ruff показывает `F401` или `I001`, это он и есть: неиспользуемый импорт или порядок импортов. Правка в том файле, на который он указал, а не отключение правила.

✅ Готово, когда обе команды молчат об ошибках.
