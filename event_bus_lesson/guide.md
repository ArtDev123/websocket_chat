# Событийная шина в памяти — обзор

Пошаговая реализация — в [README.md](README.md). Здесь — **карта**: зачем очередь между загрузкой и обработкой, что делают S3 и SQS, почему всё умещается в один процесс.

> Пишите код по шагам. На шаге 1 пакет только включает мок. Картинка, очередь и консьюмер появятся в своих файлах дальше.

---

## 1. Зачем этот урок

После загрузки файла обычно надо что-то сделать: сжать картинку, записать строку в журнал, отправить письмо. Если функция загрузки сама вызывает обработку, она знает все следующие шаги. Добавили ещё одну обработку — пришлось менять загрузку.

**Событие** — сообщение о факте, который уже случился: «файл `cat.png` загружен, вот ссылка». Загрузка только публикует факт. Обработчик сам решает, что с ним делать, и загрузку не вызывает.

Канал, по которому едут такие факты, на этом уроке — очередь. Её и называем шиной: продюсер и консьюмер связаны сообщением, а не прямым вызовом функции.

```text
прямой вызов                         шина (очередь)
────────────                         ──────────────
upload()                             upload()
   │                                    │  положил JSON
   └──► process(filename)              ▼
                                     очередь
                                        │
                                        ▼
                                     consume()  →  «Обрабатываю файл: cat.png»
```

На уроке оба живут в одном процессе, но в разных модулях. В бою это часто два разных процесса: один загрузил и ушёл, второй позже прочитал очередь.

## 2. Две разные вещи: файл и новость о файле

| | S3 | SQS |
|--|----|-----|
| Что хранит | байты картинки | текст сообщения |
| Как обратиться | имя корзины + ключ объекта | URL очереди |
| Что забираем | сам файл | JSON: имя файла и ссылка на него |

В очередь кладут **новость**, а не картинку. Картинка тяжёлая, сообщение — несколько строк. Консьюмер по имени файла понимает, что обрабатывать, по URL знает, где лежат байты.

```text
продюсер                         память процесса                      консьюмер
   │                                    │                                │
   │  put_object(cat.png)               │                                │
   │ ──────────────────────────────────►│ корзина S3                     │
   │ ◄──────── URL ─────────────────────│                                │
   │                                    │                                │
   │  send_message({"filename","url"})  │                                │
   │ ──────────────────────────────────►│ очередь SQS                    │
   │                                    │                                │
   │                                    │  receive_message               │
   │                                    │ ◄──────────────────────────────│
   │                                    │ ──────────────────────────────►│
   │                                    │                                │  печать имени
```

В настоящем AWS корзина может сама слать уведомление в SQS. Здесь сообщение отправляет скрипт: так видно, из каких полей собран JSON и кто его читает.

## 3. Почему «в памяти»

**boto3** — библиотека с методами вроде `create_bucket` и `send_message`. Обычный клиент ходит по HTTPS в AWS.

**moto** подменяет эти ответы, пока открыт блок `with mock_aws()`. Корзина и очередь появляются в оперативной памяти процесса. Вышли из блока — их больше нет. Сеть, ключи от аккаунта и оплата не участвуют.

Отсюда правило урока: создать корзину, отправить сообщение и прочитать его нужно **внутри одного** `with mock_aws()`. Консьюмер снаружи блока увидит пустоту: шина уже исчезла вместе с моком.

Учебные ключи `testing` / `testing` кладём в переменные окружения до создания клиентов. boto3 без них начинает искать настоящие креды. Мок эти значения не проверяет.

Регион везде один: `us-east-1`. Для корзины S3 в этом регионе не нужен дополнительный параметр `LocationConstraint`.

## 4. Мини-архитектура

Пакет `event_bus/`. Запуск из каталога `event_bus_lesson`: `python -m event_bus`.

```text
event_bus_lesson/
  event_bus/
    config.py       имена, регион, учебные ключи
    storage.py      S3: корзина, байты, URL
    publisher.py    SQS: очередь и send_message
    consumer.py     SQS: receive_message и печать
    main.py         mock_aws и порядок вызовов
    __main__.py     точка входа python -m event_bus
```

```text
main.py
   │  with mock_aws(): клиенты и вызовы по порядку
   │
   ├── storage.create_bucket / upload_image  →  URL
   ├── publisher.publish_upload(url)         →  JSON в очередь
   └── consumer.consume                      →  «Обрабатываю файл: …»
            │
            └── config.py  (общие имена, без boto3-вызовов)
```

| Модуль | Знает | Не импортирует |
|--------|--------|----------------|
| `config` | константы и переменные окружения | boto3, остальные модули |
| `storage` | корзину и `put_object` | очередь, консьюмера |
| `publisher` | `send_message` и JSON события | корзину, консьюмера |
| `consumer` | `receive_message`, печать, `delete_message` | корзину и `publisher` |
| `main` | порядок: мок → S3 → очередь → консьюмер | детали `put_object` и полей JSON |

`main` передаёт консьюмеру уже созданный клиент SQS и URL очереди. Имя файла консьюмер берёт из `Body`, а не аргументом от `storage`.

`mock_aws()` живёт только в `main`. Остальные модули вызывают boto3 и попадают в мок, потому что `main` зовёт их изнутри блока.

---

## 5. Что получится в конце

1. `main` включает мок.
2. `storage` создаёт корзину `lesson-uploads`, кладёт байты `cat.png`, возвращает URL.
3. `publisher` создаёт очередь `file-uploaded` и отправляет JSON `file_uploaded`.
4. `consumer` читает сообщение и печатает `Обрабатываю файл: cat.png`.
