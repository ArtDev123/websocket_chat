1. Эволюция инфраструктуры

Современная архитектура прошла долгий путь абстракции:

  • On-Premise: Управление железом, охлаждением, сетями.
  • IaaS (EC2): Аренда виртуальных машин. Вы управляете ОС (Linux/Windows) и патчами безопасности.
  • CaaS (ECS): Управление контейнерами. Изолированные среды выполнения (Docker).
  • Serverless (Lambda): Вы пишете только код. AWS масштабирует и запускает его.

2. Shared Responsibility Model

Безопасность — это разделенная ответственность.

  • AWS отвечает за облако: Физическая защита ЦОД, гипервизоры, сетевая инфраструктура.
  • Клиент отвечает за данные в облаке: Настройка политик доступа (IAM), шифрование, логика приложения.
  • Важно: В Serverless AWS берет на себя управление ОС, снимая с вас задачи администрирования.

3. Монолит vs Микросервисы

  • Монолит: Все компоненты (корзина, каталог, оплата) в одной кодовой базе. Падение одного тянет на дно всё приложение.
  • Микросервисы: Независимые компоненты. Общаются по сети (API/Очереди).
  • Плюсы: Изоляция отказов, независимое масштабирование, разные стеки технологий.

4. Event-Driven Architecture (EDA)

Событийно-ориентированная архитектура.

  • Компоненты реагируют на изменения состояния (события), а не ждут поллинга.
  • Событие (Event): Неизменяемый факт (например, "Файл загружен", "Заказ оплачен").
  • Снижает связанность (Decoupling) и позволяет масштабировать обработчики независимо.

5. Синхронность vs Асинхронность

  • Синхронно (REST): Сервис А вызывает Сервис Б и блокируется, ожидая ответа. Риск каскадных отказов.
  • Асинхронно (SQS/SNS): Сервис А кидает сообщение в очередь и сразу продолжает работу. Сервис Б забирает сообщение, когда готов.
  • Защита: Асинхронность защищает базы данных от пиков трафика (Thundering Herd).

6. Идемпотентность

Свойство операций в распределенных системах.

  • В облаке случаются сетевые сбои. Сообщение может быть доставлено дважды.
  • Идемпотентность: Повторное выполнение функции дает тот же результат, что и первое (без дублирования списания денег).
  • Реализуется через `Idempotency Key` и проверку статуса транзакции в БД (DynamoDB).

7. Amazon S3: Базовые концепции

S3 (Simple Storage Service) — объектное хранилище.

  • Buckets (Корзины): Глобально уникальные пространства имен (как диски).
  • Objects (Объекты): Файлы и их метаданные. Размер одного объекта до 5 ТБ.
  • Нет настоящих папок, есть только плоская структура ключей (например, `folder/image.jpg` — это просто длинное имя файла).

8. Надежность и Долговечность S3

  • Durability (Долговечность): 99.999999999% (11 девяток). Риск потери файла ничтожен.
  • Достигается за счет автоматической репликации каждого файла минимум в 3 физически удаленные Зоны Доступности (AZ).
  • Консистентность: Read-after-write. После PUT-запроса, последующий GET мгновенно вернет новую версию файла.

9. Классы хранения (Storage Classes)

Оптимизация стоимости хранения.

  • S3 Standard: Для горячих данных. Дорогое хранение, бесплатный доступ.
  • S3 Standard-IA: Для редкого доступа (1 раз в месяц). Дешевое хранение, плата за байты при скачивании.
  • S3 Glacier: Для архивов. Дешево, но извлечение занимает от минут до 12 часов.

10. Intelligent-Tiering и Lifecycle

  • Lifecycle Rules: Автоматическое перемещение старых файлов. "Перенести логи старше 30 дней в Glacier, через год — удалить".
  • Intelligent-Tiering: Класс с машинным обучением. Сам переносит файлы между Standard и IA в зависимости от того, как часто к ним обращаются пользователи. Идеально для неизвестных паттернов трафика.

11. Безопасность S3 и Шифрование

  • Доступ по умолчанию закрыт. Контроль через IAM Policies и Bucket Policies.
  • SSE-S3: S3 сам генерирует ключи (AES-256) и прозрачно шифрует данные на дисках.
  • SSE-KMS: Использование Key Management Service для тонкого контроля доступа и аудита каждого факта расшифровки (CloudTrail).

12. S3 Pre-signed URLs: Паттерн

Делегирование прав на загрузку/скачивание тяжелых файлов без нагрузки на сервера.

  • Бэкенд создает ссылку с подписью IAM и тайм-аутом (5 минут).
  • Пользователь напрямую загружает файл в S3 по этой ссылке.

13. Multipart Upload и Byte-Range Fetches

  • Multipart Upload: Обязательно для файлов больше 100 МБ. Файл бьется на части, загружается параллельно. При обрыве сети перекачивается только сбойный кусок.
  • Byte-Range Fetch: Использование HTTP `Range`. Позволяет скачать конкретные байты (например, только метаданные видео или резюмировать загрузку).

14. S3 Event Notifications

Превращает S3 из пассивного склада в активный триггер.

  • Событие `s3:ObjectCreated` может автоматически запустить Lambda, положить сообщение в SQS или SNS.
  • Пример: Как только в S3 упало новое фото, Lambda автоматически просыпается, делает кроп картинки для превью и сохраняет результат обратно.

15. S3 Object Lock и Versioning

  • Versioning (Версионирование): При перезаписи файла сохраняется предыдущая версия. Защита от случайного удаления (Delete Marker).
  • Object Lock (WORM): Write-Once-Read-Many. Аппаратная защита на уровне AWS. Объект невозможно удалить или изменить даже с правами Root, пока не истечет заданный срок. Обязательно для банков и аудита.

16. S3 Select и Glacier Select

Продвинутый поиск внутри файлов.

  • Обычно, чтобы найти строку в 10 ГБ CSV-файле, нужно скачать его целиком.
  • S3 Select: Позволяет отправить SQL-подобный запрос (`SELECT * FROM s3object`) прямо в S3. AWS отфильтрует данные на своей стороне и вернет вам только 5 МБ нужных строк, экономя время и трафик.

Блок 4: API Gateway

Управление трафиком на границе сети

(Слайд 18 из 50)

17. API Gateway: Типы шлюзов

  • REST API: Максимальный контроль. Поддерживает сложную трансформацию запросов, кэширование, валидацию схем и монетизацию API.
  • HTTP API: Оптимизирован для Serverless. До 71% дешевле и 60% быстрее REST API. Идеально для проксирования в Lambda без лишней логики.
  • WebSocket API: Для двусторонней связи (чаты, риал-тайм дашборды). Поддерживает постоянное соединение.

18. Защита от перегрузок (Throttling)

Алгоритм Token Bucket ("Корзина токенов") спасает ваши базы данных.

  • Rate (Скорость): Как быстро новые токены (разрешения) капают в корзину (например, 1000/сек).
  • Burst (Всплеск): Максимальный размер корзины. Позволяет обработать кратковременный спайк трафика (например, 2000 запросов разом).
  • Лишние запросы не доходят до Lambda, а мгновенно получают `429 Too Many Requests`.

19. Оптимизация: API Caching

Кэширование результатов сложных запросов.

  • Позволяет сократить количество вызовов бэкенда (Lambda) и баз данных (DynamoDB/RDS).
  • Ответ сохраняется в памяти шлюза (TTL до 1 часа).
  • Результат: Задержка (Latency) падает с 300 мс до 15 мс. Финансовая экономия на стоимости вызовов Lambda.

20. Стратегии Авторизации

  • Amazon Cognito: Встроенная проверка OIDC/JWT токенов. Не требует написания кода.
  • IAM Auth: Использование подписей AWS SigV4. Идеально для взаимодействия "сервис-сервис" (B2B).
  • Lambda Custom Authorizer: Вызов специальной Lambda для сложной кастомной логики (например, поход в старую базу данных для проверки API-ключа).

21. Продвинутые интеграции

  • Lambda Proxy Integration: HTTP-запрос передается в Lambda "как есть" (цельным JSON). Lambda сама парсит заголовки и тело.
  • AWS Service Integration: Прямое подключение API Gateway к DynamoDB или SQS!
  • Пример: API Gateway использует язык шаблонов VTL, чтобы превратить HTTP POST запрос сразу в сообщение SQS, вообще не вызывая Lambda (экономия 100% стоимости вычислений).

22. Canary Deployments

Безопасный релиз новых версий API.

  • Вы выкатываете версию API v2, но не хотите рисковать всеми пользователями.
  • Настройка Canary направляет 90% трафика на стабильную v1, и 10% трафика на новую v2.
  • Инженеры мониторят ошибки на v2. Если всё ок, доля плавно увеличивается до 100%.

Блок 5: AWS Lambda

Serverless вычисления "под капотом"

(Слайд 25 из 50)

23. Что такое AWS Lambda?

  • Компьютинг, управляемый событиями. Код запускается только когда есть триггер (S3, API GW, SQS, Cron).
  • Вы платите за Миллисекунды выполнения. 0 вызовов = $0.
  • Работает поверх Firecracker microVMs — гипервизора с открытым исходным кодом от AWS, обеспечивающего жесткую изоляцию при старте за ~125 мс.

24. Жизненный цикл вызова Lambda

Фазы работы функции:

  1. Init: Старт microVM, скачивание кода, запуск Runtime (Node/Python), выполнение кода ВНЕ хэндлера (глобальные переменные).
  2. Invoke: Выполнение самого обработчика (Handler) бизнес-логики.
  3. Shutdown: Среда "замораживается" для переиспользования или уничтожается при простое.

25. Cold Starts (Холодные старты)

  • Проблема: Фаза Init занимает время. Первый вызов Lambda после долгого простоя (или резкий скачок конкурентных вызовов) отвечает дольше на 1-3 секунды.
  • Решение 1: Писать легкий код вне хэндлера (не подключать тяжелые библиотеки).
  • Решение 2 (Provisioned Concurrency): Заплатить AWS, чтобы X сред всегда были "теплыми". Гарантирует P99 Latency < 50ms.

26. Оптимизация памяти (FinOps)

  • В Lambda вы не выбираете CPU. Вы выбираете только Объем памяти (от 128 МБ до 10 ГБ).
  • Мощность CPU выделяется пропорционально памяти. (1769 МБ = 1 полный vCPU).
  • Секрет FinOps: Поднятие памяти с 128 МБ до 1024 МБ может ускорить функцию в 10 раз. Вы заплатите за бóльшую память, но за в 10 раз меньшее время (миллисекунды) — в итоге функция станет дешевле!

27. Lambda внутри VPC (Hyperplane ENI)

Как Lambda ходит в вашу приватную базу данных (RDS):

  • Раньше Lambda прикрепляла сетевой интерфейс (ENI) при каждом холодном старте (занимало до 15 сек).
  • Сейчас AWS использует Hyperplane ENI. Интерфейс создается 1 раз при деплое.
  • Подключение "теплых" или "холодных" лямбд к VPC теперь занимает миллисекунды.

28. Асинхронные вызовы и Retries

  • Когда S3 или SNS вызывают Lambda, они делают это асинхронно. Событие падает во внутреннюю очередь AWS.
  • Если код Lambda падает с ошибкой, AWS сам повторяет вызов 2 раза с экспоненциальной задержкой.
  • Обязательно: писать код идемпотентно, иначе при Retries функция может дважды списать деньги клиента.

29. Lambda Destinations

Маршрутизация результатов асинхронных вызовов без написания кода.

  • On Success: Отправить JSON ответа в EventBridge, SQS или SNS для запуска следующего шага пайплайна.
  • On Failure: Если все 3 попытки (Retries) упали, автоматически переслать payload с причиной ошибки в DLQ (Dead Letter Queue) для разбора инженерами. Спасает от потери данных!

Блок 6: Amazon SQS

Асинхронные Очереди Сообщений

(Слайд 33 из 50)

30. Зачем нужны очереди (SQS)?

Буферизация и сглаживание пиковых нагрузок (Traffic Shaping).

  • Первый сервис AWS (запущен в 2004).
  • Вместо того чтобы "валить" базу данных 10,000 запросами в секунду, API складывает сообщения в SQS.
  • Воркеры (ECS или Lambda) вычитывают очередь с комфортной для базы скоростью. База защищена на 100%.

31. Visibility Timeout

Механизм защиты от падения воркеров.

  • Консьюмер (ECS Task) берет сообщение. Сообщение не удаляется, а становится "невидимым" для других на 30 секунд.
  • Если задача успешно выполнена, консьюмер обязан явно послать API-команду `DeleteMessage`.
  • Если консьюмер "умер" в процессе, через 30 сек сообщение снова появится в очереди, и его подхватит другой живой контейнер.

32. Amazon SNS: Pub/Sub

SNS (Simple Notification Service) — шина мгновенных уведомлений.

  • Паттерн Publish/Subscribe (Издатель/Подписчик). В отличие от SQS (Pull), SNS проталкивает (Push) сообщения подписчикам.
  • Издатель: Публикует 1 сообщение в логический "Топик" (Topic).
  • Подписчики: SQS очереди, Lambda, HTTP-вебхуки, Email, SMS.
  • Важно: SNS не хранит сообщения долго. Если подписчик недоступен длительное время, сообщение теряется (если не настроена DLQ).

33. Паттерн: Fan-out (Веерная рассылка)

Ключевой паттерн для слабосвязанных микросервисов.

  • Проблема: При новом заказе нужно уведомить Склад, Биллинг и Доставку. Прямые вызовы (REST) убьют систему при пиковой нагрузке.
  • Решение: Сервис Заказов стреляет событием в `SNS Topic`.
  • К топику подключены 3 `SQS Очереди` (Склад, Биллинг, Доставка). SNS мгновенно дублирует payload во все три очереди.
  • Микросервисы вычитывают свои SQS в комфортном для них темпе.

Блок 7: Amazon ECS и Fargate

Оркестрация контейнеров в облаке

(Слайд 38 из 50)

34. Зачем нужны Контейнеры?

  • Docker-контейнер — стандартизированный пакет, содержащий только код, библиотеки и зависимости.
  • В отличие от Виртуальной Машины, не имеет своей ОС. Использует ядро хостовой машины.
  • Плюсы: Весит мегабайты (а не гигабайты), запускается за секунды, работает абсолютно одинаково на ноутбуке разработчика и в облаке AWS.

35. Amazon ECS (Elastic Container Service)

Проприетарный оркестратор AWS (альтернатива Kubernetes).

  • Control Plane (Управляющий слой): Бесплатный мозг системы. Следит за состоянием, перезапускает упавшие контейнеры, балансирует сеть.
  • Data Plane (Слой данных): Где физически работают контейнеры. Выбирается инженером:
    • EC2 Launch Type: Вы сами администрируете серверы.
    • AWS Fargate: Вы вообще не видите серверов. Serverless для контейнеров.

36. Иерархия ECS: Cluster > Service > Task

  • Task Definition: Эскиз приложения (JSON). Какой образ скачать, сколько RAM/CPU выдать.
  • Task (Задача): Запущенный экземпляр Task Definition (один или несколько связанных контейнеров).
  • Service (Сервис): Менеджер поддержания жизнеспособности. Если вы указали 5 Tasks, и один упал (Out Of Memory), Service мгновенно поднимет новый.
  • Cluster: Логическая граница для Сервисов (сеть и IAM права).

37. Балансировка и Dynamic Port Mapping

Интеграция с Application Load Balancer (ALB).

  • Нельзя жестко задать порт 80 для контейнера, если их запускается 10 штук на одном EC2 сервере (конфликт портов).
  • ECS выдает динамические случайные порты (например, 32768) и автоматически сообщает ALB: "Новый контейнер доступен на 10.0.1.5:32768".
  • Пользователь стучится на стандартный HTTPS порт ALB (443), а ALB прозрачно проксирует трафик внутрь кластера.

38. Service Discovery (Cloud Map)

Как микросервисы находят друг друга без ALB?

  • Когда Service A хочет вызвать Service B (например, биллинг), он не может хардкодить IP, так как контейнеры постоянно умирают.
  • Решение: AWS Cloud Map (Service Discovery).
  • ECS автоматически регистрирует IP каждого нового контейнера во внутренней зоне DNS (Route 53). Service A просто делает запрос на `http://billing.internal`, и DNS возвращает список живых IP-адресов.

39. Автомасштабирование (Target Tracking)

  • Система должна расширяться и сужаться в зависимости от трафика.
  • Вы задаете метрику: Средняя загрузка CPU = 70%.
  • Если на сайт пришла толпа, CPU прыгает до 90%. ECS Auto Scaling вычисляет формулу и запускает (Scale Out) 5 новых Tasks для размазывания нагрузки.
  • Ночью CPU падает до 20%, и ECS убивает лишние контейнеры (Scale In), чтобы вы не платили за простой оборудования.

Блок 8: Продвинутые Паттерны и Сборка

(Слайд 45 из 50)

40. Паттерн Strangler Fig (Миграция)

Безопасный распил старого Монолита.

  • Переписывать всю систему с нуля — риск для бизнеса.
  • Перед монолитом ставится API Gateway. Все запросы идут в старую систему.
  • Команда пишет один новый микросервис (например, /reviews) на Lambda/ECS. API Gateway перенаправляет только путь `/reviews` в новую архитектуру.
  • Постепенно (функция за функцией) новый код "душит" монолит, пока тот не будет выключен.

41. Паттерн Saga (Распределенные Транзакции)

Консистентность данных между микросервисами.

  • В монолите есть `SQL ROLLBACK`. В микросервисах (где БД у каждого своя) его нет.
  • Если сервис Оплаты списал деньги, а сервис Склада ответил ошибкой 500 (товара нет), транзакция зависла.
  • Saga (Оркестрация): Использует AWS Step Functions как дирижера. При ошибке склада он автоматически вызывает "Компенсирующую транзакцию" (Refund) в сервисе Оплаты.

42. Финальная Архитектура: Шаг 1 (Edge)

Строим глобальное приложение обработки видео.

  • DNS: Route 53 направляет пользователя.
  • CDN: Amazon CloudFront терминирует SSL-соединение на ближайшем к пользователю Edge-узле (например, в Европе).
  • Безопасность: API Gateway с подключенным AWS WAF блокирует хакеров и ботнеты на границе сети.

44. Финальная Архитектура: Шаг 3 (Обработка)

Событийно-ориентированная магия и Fan-Out.

  • Как только 1 ГБ загружен, S3 стреляет событием `ObjectCreated` в SNS.
  • SNS клонирует сообщение в две `SQS очереди`.
  • Ветка 1 (Fargate): Читает SQS 1. Контейнер скачивает видео и жмет его в 720p (работает 15 минут). Готовое видео сохраняется в `S3 Public Bucket`.
  • Ветка 2 (Lambda): Читает SQS 2. Обновляет DynamoDB пользователя ("новое видео добавлено") за 100 мс.
  • Пользователь смотрит готовое видео через CloudFront из кэша.
