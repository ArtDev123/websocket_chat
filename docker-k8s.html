1. Карта лекции

Docker

Образ, слои, Dockerfile, кэш, пользователь, сигналы, секреты, тома. Затем вопросы, на которые ждут короткий точный ответ.

Kubernetes

Под, Deployment, Service, Ingress, конфигурация, пробы, лимиты, выкатка. База, без которой манифест читается как набор несвязанных YAML.

Как это собирают

Compose на машине разработчика. Kubernetes и ECS как два прод-контура. Общий образ, разное место для базы и разный вход трафика.

Оркестратор не чинит плохой образ. Сначала процесс правильно стартует и останавливается в одном контейнере, потом уже появляется несколько копий и балансировка.

2. Что такое контейнер

Контейнер — обычный процесс хоста. Ядро у него то же, что у машины. Изоляцию дают namespaces Linux: свой взгляд на процессы, сеть, файловую систему, имя хоста. Потолок по CPU и памяти задают cgroups. Отдельной гостевой операционной системы внутри нет.

Контейнер

  • Старт за секунды: поднимается процесс, а не ОС.
  • Образ несёт файлы приложения и библиотеки, ядро берётся с хоста.
  • Плотность выше: на одном ядре живут десятки процессов.

Виртуальная машина

  • Гипервизор, гостевое ядро, свой диск.
  • Сильнее изоляция ценой памяти и времени старта.
  • Уместна, когда нужно чужое ядро или жёсткая граница арендатора.

Образ, собранный под Linux, не запустится на хосте с другим ядром без виртуальной машины. Docker Desktop на macOS как раз прячет маленькую Linux-ВМ, и контейнеры работают уже внутри неё.

3. Образ и контейнер

Образ неизменяем. В нём слои файлов и конфигурация запуска: команда, переменные, пользователь, рабочий каталог. Контейнер — запущенный из образа процесс плюс тонкий записываемый слой сверху. Удаление контейнера забирает этот слой. Файлы, которые процесс создал и не положил на том, исчезают вместе с ним.

образслои только для чтения
+
writable layerживёт вместе с контейнером

контейнерпроцесс + сеть + слой
  • Из одного образа запускают сколько угодно контейнеров. Записываемые слои у них разные.
  • Контейнер не «сохраняют в образ» штатным путём работы. Новое содержимое получают новой сборкой Dockerfile, а не правкой живого контейнера.
  • docker commit существует и почти всегда оставляет систему, которую нельзя воспроизвести.

4. Слои

Каждая инструкция Dockerfile, которая меняет файлы, добавляет слой. Слой адресуется по содержимому. Если слой уже есть локально или в реестре, его не передают заново. Поэтому порядок инструкций и совпадение контекста сборки прямо влияют на время сборки и размер скачивания.

FROM slimбазовый слой
+
pip installменяется редко
+
COPY appменяется часто
  • Удаление файла следующим слоем не уменьшает образ: файл остаётся в предыдущем слое. Чистить кэш пакетов нужно в том же RUN, где пакеты ставились.
  • Историю слоёв видно через docker history. Секрет, попавший в RUN, остаётся в истории, даже если следующий слой удалил файл.

6. CMD, ENTRYPOINT и сигнал остановки

ENTRYPOINT задаёт исполняемый файл. CMD задаёт аргументы по умолчанию. Аргументы docker run image --port 8080 заменяют CMD и дописываются к ENTRYPOINT. Заменить сам исполняемый файл можно флагом --entrypoint.

Exec-форма

CMD ["uvicorn", "app.main:app"]. Процесс приложения становится PID 1. docker stop шлёт ему SIGTERM, ждёт таймаут (по умолчанию 10 секунд) и только потом SIGKILL. Приложение успевает дописать ответ и закрыть соединения.

Shell-форма

CMD uvicorn app.main:app превращается в /bin/sh -c "...". PID 1 — оболочка. Дочерний процесс сигнал часто не получает и умирает по SIGKILL. В скрипте запуска последней строкой должен быть exec, чтобы приложение заняло место оболочки.

Если приложение само не собирает зомби-процессы и не обрабатывает сигналы, перед ним ставят маленький init, например tini. В Kubernetes отдельного init по умолчанию нет: в спецификации контейнера тоже нужна exec-форма команды. Поле shareProcessNamespace только объединяет пространство PID контейнеров одного пода и сигналы за приложение не обрабатывает.

7. Контекст сборки

Команда docker build отправляет демону каталог контекста, обычно это .. Демон видит только этот каталог. COPY не умеет выйти наружу через ../. Лишние файлы раздувают передачу. Если их захватывает широкий COPY . ., меняется ещё и кэш этого слоя.

# .dockerignore
.git
.venv
__pycache__
.env
.env.*
tests
**/__pycache__
README.md
  • .env в контексте опасен дважды: файл может уехать в образ через широкий COPY . ., и любая правка секрета сбрасывает кэш.
  • Зависимости копируют отдельным шагом, код — следующим. Иначе каждая правка строки исходника заново ставит пакеты.
  • В .dockerignore держат и локальные артефакты сборки, и документацию, если она не нужна процессу.

8. Кэш слоёв

Кэш инструкции действителен, пока не изменились она сама и все предыдущие слои. Первая изменённая инструкция пересобирает всё, что ниже. Поэтому редко меняющееся стоит выше часто меняющегося.

  1. FROM — базовый образ.
  2. Постановка системных пакетов.
  3. COPY requirements.txt и установка зависимостей.
  4. COPY исходников.
  5. USER и команда запуска. Они дёшевы, но тоже сбрасывают кэш ниже себя, если меняются.

Кэш пакетного менеджера между сборками сохраняют монтированием BuildKit: RUN --mount=type=cache,target=/root/.cache/pip. Это кэш сборки на машине, а не слой образа. В финальный образ каталог кэша не попадает. Флаг --no-cache у команды build отключает кэш слоёв целиком и нужен, когда проверяют воспроизводимость, а не когда ускоряют обычный цикл.

9. Multi-stage сборка

В первой стадии остаются компилятор, заголовки и полный набор инструментов. В финальный образ копируют только виртуальное окружение и код. В проде нет gcc и нет оболочки, если базовый образ это позволяет. Меньше размер, меньше поверхность пакетов с известными дырами.

FROM python:3.12-slim AS build
WORKDIR /app
RUN python -m venv /opt/venv
COPY requirements.txt .
RUN /opt/venv/bin/pip install --no-cache-dir -r requirements.txt

FROM python:3.12-slim
RUN useradd --create-home --uid 10001 app
WORKDIR /app
COPY --from=build /opt/venv /opt/venv
COPY app ./app
ENV PATH="/opt/venv/bin:$PATH"
USER app
ENTRYPOINT ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8080"]

10. Базовый образ, тег и digest

Тег — подвижная метка. Сегодня python:3.12-slim указывает на один digest, через неделю сопровождающие перевесят тег на образ с другими патчами. Digest sha256:… адресует конкретное содержимое. Повторная сборка с тем же digest даёт тот же базовый слой.

  • latest в проде не говорит, какая версия запущена, и не даёт предсказуемого отката. Откат — это повторный запуск прежнего digest, а не надежда, что тег ещё не переехал.
  • Читаемый тег и digest совмещают: chat-api:1.4.2@sha256:abc…. Человеку видна версия, кластер тянет неизменяемое содержимое.
  • Базу берут минимальную под задачу: slim или distroless. Полноценный дистрибутив с оболочкой и пакетным менеджером нужен для отладки, не для каждой реплики.
  • Обновление базы — отдельное сознательное действие: пересобрать, прогнать тесты, выкатить. Плавающий тег делает это действие случайным.

11. Пользователь и корневая файловая система

Процесс в контейнере по умолчанию — root хостового ядра, ограниченный namespaces. Дыра в приложении с uid 0 внутри контейнера опаснее той же дыры от непривилегированного пользователя. Пользователя создают в образе с фиксированным uid и переключаются на него инструкцией USER до запуска.

  • Каталоги, куда процесс пишет, создают заранее и отдают этому uid. Иначе приложение падает уже после USER, и контейнер выглядит «сломанным без причины».
  • Порт 8080 не требует root. Порты ниже 1024 требуют, поэтому сервис слушает высокий порт, а снаружи его публикует прокси или Service.
  • Флаг --read-only и в Kubernetes поле readOnlyRootFilesystem запрещают запись в слой контейнера. Временным файлам отдают пустой каталог tmpfs или emptyDir.
  • Distroless-образ без оболочки убирает удобный docker exec с sh. Это приемлемая цена, если логи и метрики и так выходят наружу.

12. Healthcheck, логи и лимиты

  • HEALTHCHECK помечает контейнер как healthy или unhealthy. Статус сам по себе процесс не перезапускает. Политика restart срабатывает на завершение процесса, а не на проваленную проверку. Проверку использует Compose с условием service_healthy и оркестраторы, у которых она подключена отдельно.
  • Kubernetes инструкцию HEALTHCHECK из образа игнорирует. Живость и готовность описывают пробами в спецификации пода.
  • Логи пишут в stdout и stderr. Демон и оркестратор забирают этот поток. Файл внутри контейнера пропадает вместе со слоем и не попадает в общую систему логов.
  • Без --memory и --cpus один контейнер может забрать машину. Лимит памяти, который процесс превысил, заканчивается убийством процесса ядром.

Проверка здоровья бьёт в локальный эндпоинт процесса, например /health, и отвечает быстро. Проверка, которая ходит в соседнюю базу, смешивает «процесс жив» и «зависимость доступна». На оркестраторе из этого получается лавина перезапусков.

13. Секреты

Пароль, ключ облака и приватный токен в образ не кладут. Слой и история сборки хранят то, что команда RUN видела в своём тексте и в скопированных файлах. Удаление файла следующим слоем секрет из истории не вычищает.

  • Аргумент сборки ARG AWS_SECRET_ACCESS_KEY удобен и опасен: значение остаётся в метаданных сборки. Для секрета на время одной команды есть mount BuildKit: RUN --mount=type=secret. В слой он не записывается.
  • В рантайме секрет приходит из окружения, которое задаёт оркестратор, или из файла, смонтированного в память. Файл удобнее environment, когда нужно обновить значение без обязательной пересборки образа и когда хочется меньше шансов увидеть секрет в списке процессов.
  • .env на машине разработчика в образ не копируют. В .dockerignore он перечислен явно, даже если команда «и так помнит».
  • Реестр тоже часть границы: образ с секретом, уже отправленный в реестр, придётся считать скомпрометированным. Вычищение из git секрет из реестра не забирает.

14. Тома

Bind mount

Каталог хоста виден в контейнере как есть. На ноутбуке так подключают исходники, чтобы править код без пересборки. В проде так получают зависимость от файлов конкретной машины.

Named volume

Docker сам хранит данные в своём каталоге. Тому можно дать имя pgdata и пережить пересоздание контейнера. Это нормальный способ для локальной базы.

tmpfs

Каталог в памяти. Подходит для временных файлов и для секрета, который не должен лежать на диске. После остановки контейнера каталог пуст.

Состояние в записываемом слое контейнера — потеря данных при любом пересоздании. База, очередь с персистентностью и загруженные пользователем файлы живут на томе или во внешнем хранилище, а не в слое поверх образа.

15. Сеть одного демона Docker

  • Пользовательская bridge-сеть даёт контейнерам DNS-имена друг друга. Имя сервиса в Compose и есть такое имя: postgres, rabbitmq. На default bridge автоматического DNS по имени нет.
  • Публикация 127.0.0.1:8080:8080 открывает порт только на локальной машине. Запись 8080:8080 слушает на всех интерфейсах хоста.
  • Сеть host убирает отдельный сетевой namespace. Порты процесса сразу порты машины. Изоляции меньше, и на Docker Desktop для macOS это работает иначе, чем на Linux.
  • Контейнеры в разных пользовательских сетях друг друга по имени не видят. Это нормальный способ отделить проект от проекта на одной машине.

Дальше этой модели один демон не идёт. Несколько машин, общий виртуальный IP и самолечение числа копий — работа оркестратора, а не флага --network.

16. Сборка, которую не стыдно отдать в прод

  • Один процесс приложения на контейнер, exec-форма ENTRYPOINT, обработка SIGTERM, лог в stdout.
  • Фиксированный непривилегированный uid, запись только в заранее созданные каталоги.
  • Multi-stage, зависимости отдельным слоем, .dockerignore, очистка кэша пакетного менеджера в том же RUN.
  • Базовый образ по digest, свой тег версии тоже по digest. Тега latest в манифесте продакшена нет.
  • Секретов в слоях нет. Конфигурация окружения приходит при запуске.
  • Проверка /health отвечает про сам процесс и укладывается в короткий таймаут.
  • Образ, собранный в CI, — тот же образ, который запускают везде. На сервере прод заново не собирают.

17. Вопросы. Образ и процесс

Чем контейнер отличается от виртуальной машины?

Контейнер — процесс на общем ядре, изолированный namespaces и ограниченный cgroups. Виртуальная машина включает гостевое ядро. Поэтому контейнер быстрее стартует и плотнее садится на машину, а граница изоляции у него слабее.

Чем образ отличается от контейнера?

Образ неизменяем: слои и параметры запуска. Контейнер — процесс из этого образа и записываемый слой. Образ делят между запусками, слой у каждого контейнера свой и пропадает при удалении контейнера.

Публикует ли EXPOSE порт?

Нет. Инструкция записывает порт в метаданные. Наружу порт открывает публикация при запуске: -p у демона или поле ports в Compose. В Kubernetes наружу смотрит Service, а containerPort тоже в первую очередь описывает порт процесса.

18. Вопросы. Сборка

Почему правка одной строки кода заново скачивает все зависимости?

Кэш инвалидируется с первой изменённой инструкции и ниже. Если COPY . . стоит до pip install, любое изменение исходника меняет слой копирования, и установка пакетов выполняется снова. Зависимости копируют и ставят раньше кода.

Зачем multi-stage, если можно поставить пакеты и удалить компилятор?

Удаление в следующем слое не выкидывает файлы из предыдущего. Компилятор останется в размере образа. Отдельная стадия сборки позволяет перенести в финал только артефакт, например каталог виртуального окружения.

Чем тег отличается от digest?

Тег можно перевесить на другое содержимое. Digest вычисляется из содержимого и не переезжает. В продакшене запускают digest, тег оставляют человеку как имя версии.

19. Вопросы. Запуск и секреты

Почему контейнер не успевает завершиться чисто и получает SIGKILL?

Чаще всего PID 1 — оболочка из shell-формы CMD. SIGTERM от docker stop приходит ей, приложение его не обрабатывает, через таймаут ядро шлёт SIGKILL. Нужна exec-форма или exec в конце скрипта.

HEALTHCHECK с --restart=always перезапустит зависший процесс?

Нет, если процесс при этом не завершился. Проверка только меняет статус контейнера. Перезапуск по restart-политике связан с кодом выхода процесса. Кто именно реагирует на unhealthy, зависит от оркестратора, и это уже отдельная настройка.

Куда деть пароль базы при сборке и при запуске?

В слой образа и в ARG его не кладут. На время команды сборки, если секрет правда нужен сборке, используют mount типа secret. В рантайме пароль приходит из секрет-хранилища оркестратора переменной или файлом. .env разработчика в контекст сборки не входит.

20. Зачем оркестратор

Один демон Docker на ноутбуке умеет запустить контейнер и поднять его снова, если процесс умер, пока жива эта машина. Он не выбирает узел из десятка, не держит заданное число копий после потери машины и не даёт одному имени стабильный вход на весь парк.

  • Желаемое состояние: «API чата запущен в трёх копиях и принимает трафик с балансировщика». Оркестратор сравнивает факт с желаемым и создаёт недостающее.
  • Выкатка без простоя: новая версия поднимается рядом, старая уходит после готовности новой.
  • Размещение: есть запрос CPU и памяти, есть узлы, планировщик выбирает, куда сесть.
  • Сеть сервиса: одно DNS-имя на множество копий и убор нездоровых копий из балансировки.

Дальше два конкретных оркестратора: Kubernetes и ECS. Compose остаётся инструментом одной машины, в первую очередь машины разработчика. Docker Swarm в новых системах обычно не выбирают: его нишу заняли Kubernetes и облачные сервисы.

21. Из чего состоит кластер Kubernetes

Кластер — control plane и рабочие узлы. Control plane принимает желаемое состояние и приводит факт к этому состоянию. Узлы исполняют поды. В управляемом кластере (EKS, GKE) control plane принадлежит платформе, узлы остаются вашей зоной ответственности, если это не бессерверный режим узлов.

Control plane

  • API server — единственная дверь. kubectl и контроллеры ходят только сюда.
  • etcd — хранилище состояния кластера.
  • scheduler — выбирает узел для пода, которому узел ещё не назначен.
  • controller manager — набор циклов: Deployment, ReplicaSet, узлы, и так далее.

Узел

  • kubelet получает спецификацию пода и запускает контейнеры через container runtime.
  • kube-proxy или замена вроде eBPF программирует балансировку Service.
  • Контейнерный рантайм, например containerd. Docker Engine на узле для этого не обязателен.

Цикл называется reconcile: контроллер читает объект, смотрит факт и делает один шаг к желаемому. Команды «создай контейнер навсегда» в этой модели нет. Есть объект, за которым контроллер следит постоянно.

22. Pod

Под — минимальная единица запуска. Внутри один или несколько контейнеров. У них общий сетевой namespace, поэтому они делят один IP и общаются по localhost. Тома пода видны тем контейнерам, которым их смонтировали. Планировщик размещает под целиком на одном узле: разнести контейнеры одного пода по разным машинам нельзя.

контейнер api:8080
сайдкар метрикlocalhost:8080

  • Основной случай продакшена — один контейнер приложения в поде. Второй контейнер появляется по конкретной причине: прокси, сбор логов, адаптер. Это не повод сложить API, базу и брокер в один под.
  • Под смертен. Его можно выселить с узла. Состояние, которое обязано пережить под, лежит на томе с отдельным жизненным циклом или вне кластера.
  • У пода есть фазы. Pending значит, что контейнер ещё не запущен: нет узла, не скачался образ, не привязался том. Running не значит «готов к трафику»: готовность задаёт проба.

23. Deployment и ReplicaSet

Deployment описывает, какой шаблон пода держать и в скольких копиях. Сам он поды не создаёт напрямую: он создаёт ReplicaSet, а ReplicaSet создаёт и удаляет поды, чтобы число совпало с желаемым. Каждая выкатка — новый ReplicaSet. Предыдущий остаётся с нулём реплик и нужен для отката.

24. Service

Поды получают новые IP после каждого пересоздания. Service даёт стабильные DNS-имя и виртуальный IP и ведёт список подов, чьи метки совпали с селектором и кто прошёл проверку готовности. Клиент внутри кластера ходит на chat-api.default.svc.cluster.local, а не на IP пода.

ТипКто может прийти
ClusterIPТолько изнутри кластера. Тип по умолчанию и правильный выбор для базы, брокера и внутреннего API
NodePortПорт на каждом узле. Годится для отладки, в проде обычно перекрыт балансировщиком или Ingress

25. Ingress

Ingress описывает, как внешний HTTP и HTTPS попадают в Service: имя хоста, путь, TLS. Сам объект трафик не принимает. Его читает Ingress-контроллер — набор подов, который и является прокси. Нет контроллера — манифест Ingress ничего не меняет в сети.

26. Метки, селекторы, Namespace

Метка — пара ключ и значение на объекте. Селектор выбирает объекты по меткам. Service находит поды только так. ReplicaSet владеет подами только так. Имени пода в селекторе Service нет.

  • Метки шаблона пода включают все метки селектора Deployment. Лишняя метка на поде допустима. Недостающая метка селектора означает, что Service этот под не увидит, хотя под запущен.
  • Namespace делит имена и права: в prod и dev могут быть Service с одним и тем же коротким именем. Сеть и CPU namespace сам не делит.
  • Квоту на запросы ресурсов задаёт ResourceQuota. Сетевую изоляцию между namespace задаёт NetworkPolicy, и только если её вообще включили в кластере. Пустой кластер с двумя namespace — это два каталога имён, а не два контура безопасности.
  • RBAC привязывает права к service account пода. Приложение, которому не назначен аккаунт с узкими правами, не должно наследовать широкий доступ к API кластера.

27. ConfigMap и Secret

Образ один на все среды. Отличаются адрес базы, уровень логов, имя очереди. Это лежит в ConfigMap. Пароль и ключ лежат в Secret. Оба объекта монтируют файлом или прокидывают в переменные окружения. Смена образа для смены адреса базы не нужна.

ConfigMap

Обычный текст конфигурации. Файл, смонтированный в под, можно обновлять без пересоздания пода, если приложение само перечитывает файл. Переменная окружения из ConfigMap обновляется только с новым подом.

Secret

В манифесте значение часто показано в base64. Это кодирование, чтобы положить произвольные байты в YAML, а не шифрование. Кто имеет право читать Secret, получает секрет. Шифрование etcd и запрет на чтение через RBAC настраиваются отдельно.

Секрет в переменной окружения легко утекает в лог старта и в дамп процесса. Файл в памяти предпочтителен для настоящего ключа. В манифест git значение Secret не коммитят: его доставляет отдельный контур, например External Secrets или зашифрованный хранилищем репозиторий.

29. Requests и limits

requests — сколько CPU и памяти планировщик резервирует под контейнер, когда ищет узел. limits — потолок cgroup на уже запущенном контейнере. Это разные числа и разные последствия.

  • Память выше limit заканчивается OOMKill. Процесс убивает ядро узла, kubelet фиксирует перезапуск.
  • CPU выше limit не убивает процесс, а троттлит его. Симптом — рост задержки при живом процессе и при свободной с виду машине.
  • Под без requests планировщик считает почти бесплатным и может набить узел плотнее, чем тот выдержит. Под с завышенными requests стоит в Pending, хотя по факту память на узле свободна.
  • Если у каждого контейнера request равен limit и по CPU, и по памяти, под получает класс Guaranteed: при нехватке ресурсов на узле его выселяют последним. Под без requests и limits получает класс BestEffort, и выселяют его первым.

30. Выкатка и откат

Смена образа в Deployment создаёт новый ReplicaSet. maxSurge разрешает временно иметь больше подов, чем желаемое число. maxUnavailable ограничивает, сколько старых подов можно убрать, пока новые не готовы. Готовность определяет проба readiness, а не факт, что процесс стартовал.

  • Застрявшая выкатка почти всегда видна так: новые поды не становятся Ready. Причины — падение при старте, проба, не скачавшийся образ, нехватка requests на узлах.
  • HorizontalPodAutoscaler меняет число реплик по метрике. Он не заменяет ни пробы, ни лимиты: он только правит replicas.

31. Чего кластер сам не сделает

  • Не соберёт образ и не выберет удачный Dockerfile. В манифесте указан адрес уже собранного образа.
  • Не превращает запись на локальный диск пода в надёжную базу. Диск пода исчезнет вместе с подом, если это emptyDir.
  • Не шифрует Secret только потому, что объект называется Secret.
  • Не изолирует команды друг от друга без RBAC, ResourceQuota и NetworkPolicy.
  • Не знает про бизнес-готовность приложения, пока проба не описана. Running означает, что контейнер запущен.
  • Не заменяет миграции схемы. Их запускают отдельным шагом до того, как новый код начнёт ждать новые колонки. Две реплики, одновременно выполняющие одну и ту же неидемпотентную миграцию, — уже инцидент.

32. Вопросы. Объекты Kubernetes

Почему у пода один IP, даже если контейнеров два?

Контейнеры пода делят сетевой namespace. Слушать один и тот же порт двумя контейнерами нельзя, зато сайдкар ходит в приложение по localhost. Под целиком ставится на один узел.

Кто создаёт поды, если в git лежит только Deployment?

Контроллер Deployment создаёт ReplicaSet на каждую ревизию. Контроллер ReplicaSet создаёт и удаляет поды по селектору, пока число не совпадёт с желаемым. Ручное создание подов рядом с Deployment обходит этот контур.

Чем Service отличается от Deployment?

Deployment отвечает на вопрос, сколько подов какого шаблона должно существовать. Service отвечает на вопрос, по какому стабильному адресу в эти поды попасть. Один без другого либо не запускает процесс, либо не даёт к нему устойчивого входа.

33. Вопросы. Трафик и конфигурация

Чем Ingress отличается от Service типа LoadBalancer?

LoadBalancer публикует один Service на уровне TCP или UDP и обычно получает отдельный внешний адрес. Ingress задаёт HTTP-правила по хосту и пути и требует контроллер. Контроллер сам часто опубликован одним LoadBalancer на много приложений.

Под запущен, а запросов не получает. С чего начать?

С меток и readiness. Service выбирает поды селектором, а в EndpointSlice попадают только готовые. Чужая метка, проваленная проба или под в другом namespace объясняют пустой список чаще, чем «сломанный балансировщик».

Secret в Kubernetes зашифрован?

Base64 в YAML — кодирование. Защита складывается из RBAC на чтение объекта и из шифрования etcd, если его включили. Образ и git манифестом с расшифрованным значением эту защиту обходят.

34. Вопросы. Пробы, ресурсы, сбои

Куда вешать проверку «PostgreSQL отвечает»?

В readiness, если без базы этот под не должен получать трафик. В liveness её не кладут: короткий сбой базы перезапустит все копии приложения и усилит сбой. Liveness отвечает только на вопрос «этот процесс завис и лечится рестартом».

Под в Pending, узлы при этом живы. Что проверять?

Хватает ли на узлах CPU и памяти именно под requests, а не под фактическое потребление. Дальше — taint и nodeSelector, ошибка скачивания образа, непривязанный PVC. События пода называют причину прямо.

Что такое CrashLoopBackOff?

Контейнер запускается и сразу завершается. kubelet увеличивает паузу между попытками. Смотреть нужно лог предыдущего экземпляра и пробы: слишком жёсткая liveness на старте даёт тот же симптом, что и исключение в коде.

35. Три контура одного приложения

Приложение одно: stateless API, PostgreSQL, RabbitMQ. Меняется только то, кто запускает процессы и где лежит состояние. Образ API во всех контурах один и тот же.

37. Схема Compose

Всё происходит на одной машине. Своей control plane нет. DNS-имена выдаёт пользовательская сеть проекта Compose.

38. Где Compose заканчивается

  • depends_on без условия здоровья задаёт только порядок старта процессов. База может ещё не принимать соединения. Условие service_healthy ждёт HEALTHCHECK зависимости, и сама проверка должна быть честной, как pg_isready, а не «процесс существует».
  • docker compose up --scale api=3 поднимает три процесса на той же машине. Потери машины заменить нечем: вместе с демоном пропадает весь проект.
  • Выкатки с maxSurge и общим внешним балансировщиком в этой модели нет. compose up пересоздаёт контейнеры проекта на месте.
  • Bind mount исходников и сборка build: . на машине разработчика ускоряют цикл. В проде тот же файл с build означает сборку неизвестно из какого дерева файлов на сервере.
  • Секреты в compose-файле для локального пароля app:app приемлемы. Тот же файл с боевым паролем, закоммиченный в git, — утечка.

39. Путь запроса в Kubernetes

Клиент не знает IP подов. Он знает имя хоста. Дальше каждый уровень занимается своим: TLS и путь — Ingress, стабильный адрес и состав готовых подов — Service, процесс — под.

43. Fargate и запуск на EC2

Fargate

Задача получает CPU и память без вашего инстанса. Патчи хоста, ёмкость парка и агент ECS — забота AWS. Платить приходится за запрошенные задачей ресурсы, даже когда процесс их не занимает целиком. Свой демон на узел, GPU и произвольный доступ к хосту сюда не приносятся.

EC2 launch type

Вы описываете инстансы кластера, их AMI, автомасштабирование и агент. Задача садится на эти инстансы. Так получают GPU, особый диск и более плотную упаковку при ровной нагрузке. Вместе с этим приходят патчи ОС и простой, если ёмкость инстансов кончилась раньше, чем ёмкость сервиса.

Для API без локального состояния стартовый выбор — Fargate. EC2 launch type берут, когда появилось измеренное ограничение Fargate, а не заранее «на всякий случай». Смешивать оба в одном кластере можно через capacity providers, но это уже вторая итерация, когда профили задач реально различаются.

44. Роли, сеть и логи в ECS

  • Execution role нужна агенту, который запускает задачу: скачать образ из ECR, отдать логи в CloudWatch, прочитать секрет, чтобы подставить его при старте. Приложение этой ролью не пользуется.
  • Task role получает процесс внутри задачи. Если API читает S3 или шлёт сообщение в SQS, права лежат здесь. Роль узла или execution role для этого шире, чем нужно приложению.
  • Режим сети awsvpc даёт задаче свой сетевой интерфейс, свой частный IP и свою security group. Target group у ALB тогда типа ip, а не типа instance.
  • Security group задачи принимает трафик только от security group балансировщика и только на порт контейнера. База принимает трафик только от security group задачи.
  • Лог-драйвер awslogs забирает stdout. Файл в контейнере в CloudWatch сам не попадёт. Группу логов создают до выкатки, иначе задача падает на старте.

47. Где живёт база

API без локального состояния переносится между Compose, Kubernetes и ECS почти механически: тот же образ, другая обвязка. База так не переносится. У неё диск, резервные копии, обновление версии и долгое восстановление.

  • В Compose контейнер PostgreSQL с томом pgdata нормален. Это данные разработки, их можно создать заново.
  • В Kubernetes emptyDir для данных базы теряет их при пересоздании пода. StatefulSet с PVC сохраняет том, но бэкапы, failover и обновление мажорной версии остаются вашей эксплуатацией. Для большинства команд проще RDS или Cloud SQL.
  • В ECS задача с базой на эфемерном диске Fargate теряет данные при остановке задачи. Боевая база — RDS, security group которой принимает соединения только от задач API.
  • Миграции схемы запускают один раз на ревизию, до перевода трафика на новый код. Их не вкладывают в команду старта каждой из трёх реплик.

  • CI собирает образ один раз на коммит, прогоняет тесты и пушит digest. Следующие среды этот digest скачивают. Пересборка «того же Dockerfile» на проде уже другой контекст и другой результат.
  • От среды зависят переменные и секреты, а не набор файлов в образе. Имя базы и уровень логов не запекают через ARG в слой.

  • Откат во всех контурах — запуск предыдущего digest. Пока digest не перезаписан, откат не требует новой сборки.

50. Когда что выбирать

Compose

Compose нужен, чтобы поднять связку на ноутбуке и в простом прогоне CI. Одной команде на одной машине с учебными данными его хватает. Когда для продакшена нужна уже вторая машина, Compose перестаёт быть планом эксплуатации.

Kubernetes

Kubernetes выбирают, когда сервисов и сред несколько, нужна переносимость или в команде уже есть люди, которые ведут кластер. Разумная форма — управляемый EKS или GKE. Свой control plane на трёх виртуальных машинах ради тренировки дорог по времени дежурных.

ECS

ECS выбирают, когда продакшен остаётся в AWS и команде ближе объекты AWS, чем манифесты. Fargate снимает заботу об узлах, EKS при этом не обязателен. Брать ECS только чтобы не учить Kubernetes и сразу строить над ним свой оркестратор выигрыша не даёт.

Смешивать можно по границе, а не по случайности. Ноутбук на Compose, прод на ECS, тот же digest в ECR. Или ноутбук на Compose, прод на EKS. Два продакшен-оркестратора для одного сервиса без жёсткой причины удваивают выкатку, секреты и дежурство.

51. Ошибки, общие для трёх сред

  • Тег latest и в compose, и в Deployment, и в task definition. Откат и повторная сборка становятся гаданием.
  • Секрет в образе или в git рядом с манифестом. Оркестратор тут ни при чём: он честно раздаёт то, что ему положили.
  • База на диске, который живёт столько же, сколько процесс. В Compose это отсутствие тома, в Kubernetes — emptyDir, в Fargate — диск задачи.
  • Проверка здоровья, которая ходит в зависимость и при этом считается поводом убить процесс. На одной машине это шум, в кластере — одновременный рестарт всех копий.
  • Разный Dockerfile для локальной машины и для прода. Расходятся зависимости, пользователь и схема запуска, и прод впервые видит комбинацию, которую никто не запускал.
  • Миграция схемы в команде старта каждой копии. Пока копий одна, это терпимо. На третьей реплике две миграции встречаются в одной базе.

52. Вопросы. Выбор платформы

Зачем Compose, если прод всё равно на Kubernetes?

Compose поднимает полный локальный контур одной командой и не требует кластера на ноутбуке. В прод его файл не копируют. В прод уходит образ, собранный тем же Dockerfile, с другим описанием запуска.

Чем ECS отличается от EKS?

ECS — отдельный оркестратор AWS: task definition, service, desired count. EKS — Kubernetes, control plane которого ведёт AWS: поды, Deployment, Service, Ingress. Общие только регион, VPC, ECR и то, что оба умеют держать несколько копий контейнера.

Чем task definition отличается от Deployment?

Task definition описывает одну задачу: контейнеры, CPU, память, роли, логи. Число копий и выкатку задаёт уже service ECS. Deployment в Kubernetes совмещает шаблон пода и желаемое число реплик в одном объекте, а сетевой вход выносит в Service.

53. Вопросы. Собрать продакшен

Зачем задаче ECS две IAM-роли?

Execution role нужна инфраструктуре запуска: забрать образ, записать логи, достать секрет. Task role нужна коду приложения, когда оно само ходит в API AWS. Одна широкая роль на оба случая даёт процессу права агента, которые ему не нужны.

Куда деть PostgreSQL в каждом контуре?

Локально — контейнер с named volume. В Kubernetes и в ECS для боевых данных — управляемая база в частной сети. Диск пода, emptyDir и эфемерный диск Fargate переживают процесс не дольше, чем сам процесс.

Как провести версию от коммита до отката?

CI собирает образ один раз и пушит digest. Compose разработчика может собирать локально, прод только скачивает этот digest. Откат указывает предыдущий digest в Deployment или в ревизии task definition. Новая сборка для отката не нужна.

54. Вопросы. Fargate, выкатка, depends_on

Когда API сажают на Fargate, а когда на EC2 launch type?

На Fargate сажают задачу, пока ей не нужны GPU, особый доступ к хосту или уже посчитанная экономия плотной упаковки. EC2 launch type добавляет AMI, патчи узлов и отдельную ёмкость инстансов. Эти возможности не бесплатны.

Как проходит выкатка без простоя в Kubernetes и в ECS?

В Kubernetes новый ReplicaSet поднимает поды, readiness пускает их в Service, старые уходят в пределах maxUnavailable и maxSurge. В ECS новая ревизия task definition поднимает задачи, ALB видит свой health check, minimumHealthyPercent не даёт убить старые раньше времени. В обоих случаях признак готовности — проверка, а не факт старта процесса.

Гарантирует ли depends_on, что база уже принимает запросы?

Нет, если не задано условие service_healthy и у базы нет HEALTHCHECK, который проверяет приём соединений. Обычный depends_on ждёт старт контейнера зависимости. Процесс базы к этому моменту может ещё поднимать файлы.

55. Что зафиксировать

  • Контейнер — процесс на общем ядре. Образ неизменяем. Записываемый слой и всё, что в нём лежит без тома, живёт вместе с контейнером.
  • Сборка: редкие слои выше частых, multi-stage, непривилегированный uid, exec-форма, секрет мимо слоёв, digest вместо latest.
  • В Kubernetes под исполняет, Deployment держит число через ReplicaSet, Service даёт адрес, Ingress разбирает HTTP при наличии контроллера. Проба readiness управляет трафиком, проба liveness — рестартом.
  • Compose собирает одну машину разработчика. ECS и Kubernetes собирают прод. EKS — это Kubernetes, ECS — другой API.
  • Образ один, его собирает CI. База в проде управляемая. Секреты и адрес базы приходят окружением, а не новой сборкой.

Короткий самопроверка. Назвать PID 1 при shell-форме CMD. Назвать объект, который создаёт поды Deployment. Назвать две IAM-роли задачи ECS и сказать, какая из них есть у процесса приложения.
